# Criteria-Based Evaluation of MODRISS: audited 2026-09-27

## Protocol and source fidelity

Source: Eidi and Ramsin (2026), _Model-Driven Approaches for Serverless Software Development: Evaluation and Future Directions_, MODELSWARD, 560–567, [DOI](https://doi.org/10.5220/0014634200004058), supplied `.idea/process_papers/Eidi.pdf`. Tables 1–3 (pp.563–564) define the criteria; §3 defines Simple, Scale and Narrative types. This revision supersedes the earlier optimistic ratings.

**A/B/C** mean full/partial/no feature coverage for ordinary Scale criteria within the declared serverless/AWS scope. **Yes/No** is retained for the two Simple criteria. Definition Type and Application Scope are Narrative categories. Methodology Type is labeled Scale in the paper but defines A=pure model-driven and B=extension of traditional methods; those labels are categories, never maturity scores.

Design rates the specified method; realization rates concrete repository support, including manual work where the criterion does not demand automation. Missing automation alone does not disqualify a method. Conversely, prose, classifier counts and generated test shells do not prove full support. All criteria are retained, with observability divided into tracing and logging following Table 6: **20 general + 24 MDD + 34 serverless = 78 rows**.

These are single-assessor analytical feature judgments. Practitioner effectiveness is **not evaluated for every row**: no real team or comparative outcome was observed. A means feature coverage, never proven usefulness. Provisional B judgments state their limits. No aggregate percentage or comparative superiority over the paper’s older approaches is justified.

Evidence: [ReturnFlow enactment and defect log](14-returnflow-enactment-audit.md), [verification record](evaluation/returnflow/verification.md), and the paths below. ColdChain CSVs are generated coverage inventories, not independent execution evidence. Existing sample reports, including OrderPulse, are historical repository evidence and were not rerun here.

## Interpretation, weaknesses and future improvement

MODRISS has a substantial forward modeling framework and a detailed lifecycle specification. The defensible conclusion is readiness to prepare a controlled pilot, not demonstrated company-wide usability. ReturnFlow identifies useful repairs but leaves real G2–G7 acceptance unperformed. Practical smoothness remains an empirical question.

Priorities: evidence provenance/enforcement; unassisted learning and gate overhead; application completion and independent fault oracles; external-effect recovery; trace closure; AWS dependence; absent general reverse engineering; and manual runtime-to-model feedback. Code generation, semantic checking and process guidance solve distinct problems; none replaces the others.

Implement ReturnFlow using actual model/transform/build/test artifacts; execute small-team and contrasting practitioner cases under [09-empirical-validation-protocol.md](09-empirical-validation-protocol.md); measure review delay, evidence effort, rework, defects, outcomes and costs. Compare matched work against previous practice and record expertise/tooling as rival explanations before attributing benefit. Have independent assessors re-rate all 78 rows and preserve disagreements. Test additional domains/providers before domain-completeness or portability claims.

Assistant apply/repair/commit gates only structural Ecore/EMF conformance via `ModelService.validateStructural(...)`. Explicit user/model EVL workflows supply separate semantic evidence; this evaluation does not add EVL to assistant gating.
