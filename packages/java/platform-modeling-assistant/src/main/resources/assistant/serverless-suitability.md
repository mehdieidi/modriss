# MODRISS serverless suitability criteria

Version: 1.0 | Reviewed: 2026-10-25 | Task: Phase 0, assess feasibility and serverless suitability (MF-02).

## Scope

MODRISS is a methodology for serverless software development. Use these criteria during inception to decide whether a project, or a useful part of it, can be developed with MODRISS. Assess the requirements before choosing which components to model.

Serverless includes managed backend services and several forms of compute. A FaaS restriction applies to the service and plan concerned. Object-oriented code and microservice architectures can both run on serverless platforms, so neither the architectural style nor the application domain settles the decision.

The criteria draw on selected academic studies and provider documentation. The assessment procedure and the MODRISS modeling boundary are engineering judgments based on those sources. Their predictive accuracy, including the accuracy of LLM recommendations, has not been validated. Check current quotas and prices with the provider; historical measurements cannot establish them. Any claimed savings, certification, benchmark result or probability needs its own evidence.

## Assessment procedure

1. Identify the components, events, workload characteristics and mandatory requirements. Record the passages that support each finding. Keep assumptions and conflicting statements separate from confirmed requirements, and assess all criteria C01 to C12.
2. Assign each criterion one status: COMPATIBLE, CONDITIONAL, INCOMPATIBLE or UNKNOWN. For CONDITIONAL, specify the mitigation or experiment needed. Use UNKNOWN when information needed for a decision is missing or contradictory. Name the affected component and identify any hard blocker.
3. Treat a conflict as a hard blocker when a non-negotiable requirement cannot be met by the proposed deployment and no acceptable mitigation exists. Other benefits cannot compensate for it. An unspecified requirement cannot count as evidence of compatibility. State, relational data, machine learning, regulation, steady demand or WebSockets each need assessment; none is sufficient grounds for rejection on its own.
4. Choose one of the outcomes below and explain the conditions that remain.
5. Base confidence on the completeness of the evidence. HIGH confidence is inappropriate while decisive questions remain unanswered. Review the assessment when requirements, provider plans, prices, quotas or modeling and generation support change. The project team uses the result at G0; project authorization and model creation require separate decisions.

| Outcome                  | When to use it                                                                                                                                                                                                       |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SUITABLE                 | A useful serverless implementation fits the stated requirements and MODRISS scope. Record any conditions that must be met before adoption.                                                                           |
| HYBRID                   | A useful serverless subset fits. Other components can be delivered separately and connected through explicit contracts.                                                                                              |
| UNSUITABLE               | Mandatory constraints prevent a useful MODRISS serverless subset, or the project forbids the separation it would require. A decisive blocker can justify this outcome even if unrelated requirements remain unknown. |
| INSUFFICIENT_INFORMATION | Missing or conflicting information prevents a decision. Ask specific questions and explain which answers would support each alternative.                                                                             |

## Common workload patterns

These are starting points for assessment. The conditions in the last column still apply.

| Candidate                                                        | Likely design to investigate                                                        | Essential condition                                                                                          |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Web/mobile backends, webhooks, sporadic CRUD                     | Functions with managed API and data services                                        | Check latency, transaction semantics and database connections (C03 to C05).                                  |
| IoT ingestion, file processing, scheduled jobs                   | Queues or events, bounded workers and durable storage                               | Check burst limits, data size, duplicate delivery and task resources (C01 to C05).                           |
| Multi-step approvals or order workflows                          | Durable orchestration or event choreography                                         | A long workflow can consist of short invocations. Specify compensation (C02, C05 to C06).                    |
| GPU training, continuous simulation, media engines, legacy cores | External compute or APIs with serverless ingestion, orchestration or notifications  | Separation must preserve mandatory requirements and leave a useful serverless subset (C02 to C03, C09, C12). |
| Hard real-time control or required disconnected execution        | A local or specialized core, with asynchronous external integration where permitted | Reject MODRISS if no useful serverless subset is permitted (C03, C08 to C09).                                |

For each hybrid interface, specify the protocol and direction of calls, data ownership, authentication, timeouts, retries and idempotency. Assign an owner and agree on SLOs, failure handling and reconciliation. Missing details become conditions to resolve before adoption.

External services are delivered separately; MODRISS does not generate their internals. Long jobs and accelerator workloads may fit other managed compute products. Serverless containers also need a support check before they can be included in a MODRISS generation path. Structural model conformance alone cannot establish correct runtime behavior.

## Sources and review record

The literature search, conducted on 2026-10-25, covered serverless application characteristics, FaaS development in industry, performance reviews and provider architecture and hosting guidance. Sources include peer-reviewed empirical studies and surveys, together with first-party technical documentation. Unattributed blogs and marketing claims were excluded. Where publisher access was restricted, the review used the author manuscript or the IBM author abstract identified below.

This was a selective review without a formal screening or risk-of-bias protocol. Historical measurements are used to explain tradeoffs, not to set current platform thresholds.

- A1: Eismann et al. (2021), _Serverless Applications: Why, When, and How?_, IEEE Software 38, 32-39. [DOI](https://doi.org/10.1109/MS.2020.3023302); [author manuscript](https://arxiv.org/html/2009.08173). Describes 89 applications and their adoption characteristics. The observations do not establish a causal test of suitability.
- A2: Scheuner & Leitner (2020), _Function-as-a-Service performance evaluation: A multivocal literature review_, Journal of Systems and Software 170, 110708. [DOI](https://doi.org/10.1016/j.jss.2020.110708); [author manuscript](https://arxiv.org/html/2004.03276). Reviews 112 studies. Performance findings depend on the experimental setup and whether results can be reproduced.
- A3: Shafiei, Khonsari & Mousavi (2022), _Serverless Computing: A Survey of Opportunities, Challenges, and Applications_, ACM Computing Surveys 54(11s), 239. [DOI](https://doi.org/10.1145/3510611); [author manuscript](https://arxiv.org/html/1911.01296). Reviews application domains and technical challenges. Platform restrictions reported in the paper need checking against current services.
- A4: Leitner, Wittern, Spillner & Hummer (2019), _A mixed-method empirical study of Function-as-a-Service software development in industrial practice_, Journal of Systems and Software 149, 340-359. [DOI](https://doi.org/10.1016/j.jss.2018.12.013); [IBM author abstract](https://research.ibm.com/publications/a-mixed-method-empirical-study-of-function-as-a-service-software-development-in-industrial-practice). Discusses service composition and development tooling. Only the author abstract was reviewed.
- I1: AWS, [Fargate or Lambda decision guide](https://docs.aws.amazon.com/decision-guides/latest/decision-guides/fargate-or-lambda.html). Compute choices and hybrid designs for these services.
- I2: AWS, [Designing Lambda applications](https://docs.aws.amazon.com/lambda/latest/dg/concepts-application-design.html). Guidance on state, coupling, orchestration and idempotency.
- I3: AWS, [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html). Quotas must be checked for the actual account, region, invocation mode and plan.
- I4: Microsoft, [Azure Functions hosting options](https://learn.microsoft.com/en-us/azure/azure-functions/functions-scale). Scaling, networking, execution and cold starts vary by plan.
- I5: AWS, [Lambda best practices](https://docs.aws.amazon.com/lambda/latest/dg/best-practices.html). Retry-safe handlers and operational safeguards.
- M1: Repository: `apps/landing/src/main.tsx` and the Phase 0/MF-02 process definitions. These define the methodology's scope and decision responsibilities; they are project sources rather than independent academic evidence.
- M2: Repository: `methodology/modeling-framework/samples/architecture-patterns/arch-hybrid/README.md`. Describes the adapter and external-system pattern and its implementation obligations. Check exact support against current metamodels and transformation and generation profiles.
