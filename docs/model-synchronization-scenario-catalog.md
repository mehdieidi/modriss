# Iterative model synchronization scenario catalog

This document catalogs the meaningful scenarios that can occur when a model is generated, manually
refined, and regenerated as its upstream model evolves. It is intended as a requirements reference,
test-design checklist, and shared vocabulary for CIM-to-PIM and PIM-to-PSM synchronization.

The same catalog applies at either adjacent model boundary:

```text
Upstream = CIM   and Downstream = PIM
Upstream = PIM   and Downstream = AWS PSM
```

PSM-to-artifact generation is covered separately near the end because files use regeneration and
protected-region semantics rather than EMF three-way model merging.

## 1. Core states and terms

Every synchronization cycle has three inputs:

| Term             | Meaning                                                                  |
| ---------------- | ------------------------------------------------------------------------ |
| **Base**         | Exact raw downstream model generated by the last accepted transformation |
| **Working**      | Current downstream model, including user refinements since Base          |
| **NewGenerated** | Fresh raw downstream model generated from the current upstream model     |

The comparison orientation is:

```text
origin = Base
left   = Working / manual side
right  = NewGenerated / generator side
```

After a successful synchronization:

```text
Working = accepted merged result
Base    = exact raw NewGenerated model
```

The merged Working model must never be saved as Base. Otherwise, a later cycle cannot distinguish
manual edits from generated content.

### Change vocabulary

For any element or feature, each side can be:

- unchanged from Base;
- added;
- edited;
- deleted;
- moved to another containment owner;
- reordered in an ordered collection; or
- changed indirectly because another element or reference changed.

A **non-conflicting change** has one unambiguous result based on Base. A **real conflict** means the
manual and generated sides made incompatible changes to the same semantic state. A conflict is not
the same as a validation failure: a merge can be unambiguous but still produce a semantically invalid
model.

## 2. Lifecycle and baseline scenarios

| ID   | Scenario                                                             | Expected result                                                                                                                    |
| ---- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| L-01 | No Working model and no Base exist                                   | Generate fresh target; save it as both Working and raw Base                                                                        |
| L-02 | Working exists but no trustworthy Base exists                        | Return `BOOTSTRAP_REQUIRED`; do not overwrite Working or guess history                                                             |
| L-03 | Base and Working exist and upstream is unchanged                     | Idempotent no-op; no duplicates, conflicts, or semantic changes                                                                    |
| L-04 | Upstream revision changed but fresh output is semantically unchanged | No-op merge; advance source metadata safely if required                                                                            |
| L-05 | Transformation is repeated after an accepted merge                   | Use the last raw NewGenerated as Base and the accepted result as Working                                                           |
| L-07 | Working model was deleted                                            | Handle as an explicit lifecycle condition; do not silently recreate it against stale baseline history                              |
| L-08 | Source model was deleted                                             | Transformation relationship can no longer run; retain or explicitly clean downstream history according to project lifecycle policy |
| L-09 | Base record is missing or corrupted                                  | Fail safely; canonical Working remains unchanged                                                                                   |
| L-10 | Working XMI is missing but legacy JSON exists                        | Reconstruct only through the supported legacy import path, then validate before comparison                                         |

## 3. Complete element and feature change matrix

The following table is the fundamental three-way decision matrix. “Manual” means the difference
between Working and Base. “Generated” means the difference between NewGenerated and Base.

| ID   | Manual side                                          | Generated side                | Classification          | Expected result                                    |
| ---- | ---------------------------------------------------- | ----------------------------- | ----------------------- | -------------------------------------------------- |
| M-01 | unchanged                                            | unchanged                     | no change               | Keep existing value or element                     |
| M-02 | unchanged                                            | edited                        | safe incoming edit      | Apply generated edit automatically                 |
| M-03 | edited                                               | unchanged                     | safe manual edit        | Preserve manual edit automatically                 |
| M-04 | edited to X                                          | edited to X                   | convergent edit         | Accept X without conflict                          |
| M-05 | edited to X                                          | edited to Y                   | real edit/edit conflict | Require `KEEP_USER` or `TAKE_GENERATED`            |
| M-06 | absent                                               | added by generator            | safe generated addition | Add generated element automatically                |
| M-07 | added by user                                        | absent from generated history | safe user addition      | Preserve user-created element automatically        |
| M-08 | equivalent element independently added on both sides | same compatible state         | convergent addition     | Match by identity and keep one element             |
| M-09 | same identity independently added on both sides      | different state               | add/add conflict        | Require a decision for incompatible features       |
| M-10 | unchanged generated element                          | deleted by generator          | safe generated deletion | Delete obsolete generated element automatically    |
| M-11 | edited by user                                       | deleted by generator          | delete/change conflict  | Require keep subtree or accept generated deletion  |
| M-12 | deleted by user                                      | unchanged by generator        | safe user deletion      | Preserve deletion automatically                    |
| M-13 | deleted by user                                      | edited by generator           | delete/change conflict  | Require keep deletion or restore generated version |
| M-14 | deleted by user                                      | deleted by generator          | convergent deletion     | Keep deleted without conflict                      |
| M-15 | moved by user                                        | unchanged by generator        | safe manual move        | Preserve user containment move                     |
| M-16 | unchanged                                            | moved by generator            | safe generated move     | Apply generated containment move                   |
| M-17 | moved to same owner on both sides                    | same move                     | convergent move         | Apply once without conflict                        |
| M-18 | moved to different owners                            | incompatible moves            | move/move conflict      | Require manual choice                              |
| M-19 | moved by one side                                    | deleted by the other          | move/delete conflict    | Require manual choice                              |

This matrix applies recursively to nested objects. A generated deletion of a container must account
for its complete containment subtree and references; it must not leave half of the subtree behind.

## 4. Scalar attribute scenarios

Scalar attributes include names, descriptions, timeouts, statuses, flags, thresholds, configuration
values, and other single-valued properties.

| ID   | Example                                                       | Expected behavior                                                    |
| ---- | ------------------------------------------------------------- | -------------------------------------------------------------------- |
| A-01 | User changes `timeout` from 30 to 60; generator remains at 30 | Preserve 60                                                          |
| A-02 | User leaves timeout at 30; generator changes it to 45         | Apply 45                                                             |
| A-03 | Both change timeout to 60                                     | Accept 60 without conflict                                           |
| A-04 | User changes timeout to 60; generator changes it to 45        | Report conflict                                                      |
| A-05 | User clears an optional value; generator leaves Base value    | Preserve cleared value                                               |
| A-06 | User clears a value; generator changes it                     | Report conflict                                                      |
| A-07 | Generator clears a value; user leaves it unchanged            | Apply generated clearing                                             |
| A-08 | Attribute changes representation but not semantic value       | Normalize and treat as equal where the metamodel defines equivalence |
| A-09 | Display name changes but stable ID does not                   | Treat as an edit, not element replacement                            |
| A-10 | Stable immutable ID is edited                                 | Reject the mutation; IDs are not mergeable user properties           |

Scalar conflicts support `KEEP_USER` and `TAKE_GENERATED`. `KEEP_BOTH` is meaningless for a
single-valued feature and must not be offered.

## 5. Collection scenarios

Collections can be containment lists, non-containment reference lists, or multi-valued attributes.

| ID   | Scenario                                                | Expected behavior                                                        |
| ---- | ------------------------------------------------------- | ------------------------------------------------------------------------ |
| C-01 | User and generator add different members                | Preserve both additions automatically                                    |
| C-02 | Both add the same stable-ID member                      | Keep one matched member                                                  |
| C-03 | Both remove the same member                             | Remove it without conflict                                               |
| C-04 | User removes member A; generator adds member B          | Apply both independent changes                                           |
| C-05 | User edits member A; generator adds member B            | Preserve edit and add B                                                  |
| C-06 | User edits member A; generator removes A                | Delete/change conflict                                                   |
| C-07 | User removes member A; generator edits A                | Delete/change conflict                                                   |
| C-08 | Both reorder an ordered list identically                | Accept order without conflict                                            |
| C-09 | Both reorder an ordered list differently                | Order conflict when order is semantically significant                    |
| C-10 | List order changes but order is semantically irrelevant | Canonicalize or ignore ordering noise                                    |
| C-11 | Same logical member is duplicated                       | Match by stable ID and enforce uniqueness; do not keep duplicate objects |
| C-12 | Independent additions are both semantically legal       | “Keep both” is naturally achieved by the automatic union                 |

`KEEP_BOTH` should only be an explicit resolution when two conflicting additions can legally coexist
and can be assigned distinct identities. It must not be used to conceal an identity collision,
cardinality violation, or duplicate semantic role.

## 6. Containment and nested subtree scenarios

| ID   | Scenario                                                                   | Expected behavior                                                         |
| ---- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| T-01 | Generator adds a complete nested subtree                                   | Add the root, every child, and all valid internal references              |
| T-02 | Generator removes an untouched subtree                                     | Remove the complete subtree and obsolete links                            |
| T-03 | User edits a nested child while generator changes an unrelated sibling     | Preserve child edit and apply sibling change                              |
| T-04 | User edits any child while generator removes its ancestor                  | Present one logical delete/change decision for the meaningful subtree     |
| T-05 | User keeps a generator-deleted container                                   | Keep its complete locally valid subtree and required support references   |
| T-06 | User accepts generator deletion                                            | Remove the whole generated subtree, not selected fragments                |
| T-07 | Child moves between existing parents                                       | Apply safe one-sided move or report incompatible two-sided move           |
| T-08 | Child moves under a parent newly added on the same side                    | Apply parent before child and preserve dependency order                   |
| T-09 | Parent is deleted while another change points a new reference to its child | Report or reject the incompatible graph; never persist dangling links     |
| T-10 | Required containment child disappears accidentally during merge            | Reject as structurally invalid; do not repair by inventing domain content |

## 7. Reference and relationship scenarios

References include service membership, workflow edges, schema bindings, function invocations,
security relationships, trace endpoints, and any other non-containment link.

| ID   | Scenario                                                   | Expected behavior                                                           |
| ---- | ---------------------------------------------------------- | --------------------------------------------------------------------------- |
| R-01 | Generator adds a link between existing elements            | Add link automatically if user did not change the same feature              |
| R-02 | Generator removes an untouched link                        | Remove link automatically                                                   |
| R-03 | User adds a link; generator is unchanged                   | Preserve link                                                               |
| R-04 | User removes a link; generator is unchanged                | Preserve removal                                                            |
| R-05 | User and generator select different scalar targets         | Reference conflict                                                          |
| R-06 | Both select the same target                                | Convergent change; no conflict                                              |
| R-07 | Referenced target is deleted on one side                   | Remove/update link consistently or report delete/change conflict            |
| R-08 | Newly generated subtree contains cross-references          | Rebind by stable ID into Working; no temporary-resource proxies may remain  |
| R-09 | Opposite navigation changes because canonical link changed | Avoid duplicate conflict noise from derived/opposite features               |
| R-10 | Reference points to missing or wrong-type ID               | Structural failure; canonical models and Base remain unchanged              |
| R-11 | Circular references are valid in the metamodel             | Preserve the graph without duplicating elements or breaking identity        |
| R-12 | External/cross-resource reference is intentional           | Preserve only when supported and resolvable by the storage/loading contract |

## 8. Identity, rename, and traceability scenarios

| ID   | Scenario                                                         | Expected behavior                                                          |
| ---- | ---------------------------------------------------------------- | -------------------------------------------------------------------------- |
| I-01 | Source element is renamed but keeps its ID                       | Generated target keeps its deterministic ID; rename is an edit             |
| I-02 | Source element is deleted and a similarly named element is added | Treat as deletion plus addition, not rename, because identity changed      |
| I-03 | Two elements have the same display name but different IDs        | Keep them distinct                                                         |
| I-04 | Duplicate IDs appear in one logical model                        | Validation error; do not merge or persist ambiguous identity               |
| I-05 | Persisted element has no ID                                      | Validation error                                                           |
| I-06 | User-created downstream element receives an ID                   | Generate it once and keep it immutable through later cycles                |
| I-07 | Same transformation is rerun from an empty target                | Corresponding generated objects receive identical IDs                      |
| I-08 | One source creates multiple target roles                         | Each role receives a distinct deterministic ID                             |
| I-09 | TraceLink is regenerated                                         | Match and update the existing stable trace link rather than duplicating it |
| I-10 | Target survives but source trace metadata changes                | Apply generator-owned trace metadata consistently                          |
| I-11 | User changes generator-owned trace endpoint data                 | Generator policy restores canonical generated trace data                   |
| I-12 | `manuallyMaintained` is true                                     | Continue normal three-way comparison; the flag is not blanket ownership    |

## 9. Independent and combined edit scenarios

Real modeling sessions normally contain many simultaneous changes. Classification is performed per
semantic difference, not once for the entire model.

| ID   | Combined scenario                                                   | Expected result                                                                                     |
| ---- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| X-01 | User edits A; generator edits unrelated B                           | Auto-merge both                                                                                     |
| X-02 | User adds A; generator adds unrelated B                             | Preserve both                                                                                       |
| X-03 | User deletes A; generator edits unrelated B                         | Preserve deletion and apply B                                                                       |
| X-04 | Ten safe changes and one real conflict                              | Build pending candidate with safe changes, but do not commit canonical Working or Base              |
| X-05 | Multiple conflicts in different elements                            | Present separate logical decisions                                                                  |
| X-06 | Many low-level EMF differences describe one deleted subtree         | Collapse them into one understandable logical conflict                                              |
| X-07 | One conflict decision affects dependent differences                 | Apply the decision consistently to the complete dependency closure                                  |
| X-08 | User-created element references a generated element that is deleted | Report a meaningful dependency/delete conflict rather than leaving a dangling reference             |
| X-09 | Upstream edit propagates through CIM→PIM and then PIM→PSM           | Complete and validate the first boundary before using its accepted Working model as the next source |
| X-10 | User refines both PIM and PSM across several cycles                 | Preserve refinements independently at each transformation relationship and baseline                 |

## 10. Automatic merge and policy scenarios

Automatic resolution is deterministic policy, not an arbitrary “prefer latest” strategy.

| Policy            | Automatic behavior                                                                     |
| ----------------- | -------------------------------------------------------------------------------------- |
| `THREE_WAY`       | Use Base history; apply one-sided changes and report incompatible two-sided changes    |
| `GENERATOR_OWNED` | Prefer generated value, including generated trace metadata                             |
| `USER_OWNED`      | Preserve user value; use only for explicitly designated features                       |
| `IMMUTABLE`       | Reject changes, notably stable `id`                                                    |
| `IGNORE`          | Exclude derived, transient, volatile, inverse-navigation, or infrastructure-only noise |

Automatic outcomes include:

- generated-only edits, additions, deletions, and moves;
- manual-only edits, additions, deletions, and moves;
- identical/convergent changes;
- independent changes to different features or elements;
- legal union of independent collection additions;
- normalization of explicitly non-semantic ordering or representation; and
- policy-controlled generator/user ownership.

The system must not automatically resolve a real `THREE_WAY` conflict merely because one change is
newer, larger, or marked `manuallyMaintained`.

## 11. Manual conflict resolution scenarios

### KEEP_USER

`KEEP_USER` means retain the Working/left result for the conflicting semantic difference.

| ID   | Conflict                          | Meaning of `KEEP_USER`                    |
| ---- | --------------------------------- | ----------------------------------------- |
| U-01 | edit/edit                         | Keep manually edited value                |
| U-02 | generated deletion vs manual edit | Keep the manually refined element/subtree |
| U-03 | manual deletion vs generated edit | Keep the element deleted                  |
| U-04 | move/move                         | Keep manual containment owner/location    |
| U-05 | reference/reference               | Keep manual target or membership          |

### TAKE_GENERATED

`TAKE_GENERATED` means accept NewGenerated/right for the conflicting semantic difference.

| ID   | Conflict                          | Meaning of `TAKE_GENERATED`                      |
| ---- | --------------------------------- | ------------------------------------------------ |
| G-01 | edit/edit                         | Use generated value                              |
| G-02 | generated deletion vs manual edit | Delete the complete generated element/subtree    |
| G-03 | manual deletion vs generated edit | Restore the generated element with its new state |
| G-04 | move/move                         | Use generated containment owner/location         |
| G-05 | reference/reference               | Use generated target or membership               |

### Mixed decisions

A session can keep user changes for some conflicts and take generated changes for others. After all
decisions are supplied, Varka must replay the same normalized three-way comparison, apply decisions
and dependencies, validate the complete candidate, and commit atomically. A decision is not a
request to bypass structural or semantic validity.

### Cancel, defer, and rebase

| ID   | Scenario                                        | Expected behavior                                                           |
| ---- | ----------------------------------------------- | --------------------------------------------------------------------------- |
| D-01 | User leaves session unresolved                  | Keep session pending; canonical Working and Base remain unchanged           |
| D-02 | User cancels session                            | Delete pending session; keep canonical Working and Base unchanged           |
| D-03 | User resolves only some conflicts               | Store partial decisions but reject finalization                             |
| D-04 | User changes Working while session is pending   | Mark/reject session as stale; do not apply old decisions                    |
| D-05 | Upstream changes while session is pending       | Reject stale session or regenerate/rebase through a new synchronization run |
| D-06 | Baseline advances through another accepted run  | Reject old session by baseline version/fingerprint                          |
| D-07 | Same conflict is regenerated after cancellation | Create a new session from current Base, Working, and NewGenerated states    |

## 12. Validation scenarios

Validation and comparison answer different questions:

- comparison asks which changes belong in the candidate;
- structural validation asks whether the EMF graph conforms to Ecore; and
- explicit modeling-workflow EVL validation asks whether the model satisfies semantic rules.

| ID   | Scenario                                                                | Expected behavior                                                            |
| ---- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| V-01 | Source fails required transformation validation                         | Do not run/accept transformation; downstream states remain unchanged         |
| V-02 | Fresh generated target is structurally invalid                          | Fail generation; do not compare or advance Base                              |
| V-03 | Safe automatic merge is structurally invalid                            | Reject candidate; Working and Base remain unchanged                          |
| V-04 | Safe automatic merge has EVL errors                                     | Return `VALIDATION_FAILED`; Working and Base remain unchanged                |
| V-05 | Candidate has warnings only                                             | Report warnings and apply according to validation policy                     |
| V-06 | Manually resolved candidate is invalid                                  | Reject finalization; retain pending session and canonical states             |
| V-07 | Validation service cannot load XMI because of proxies                   | Treat as structural failure and report exact unresolved references           |
| V-08 | Duplicate/missing IDs are found                                         | Reject before identity-based synchronization can corrupt matching            |
| V-09 | Previously valid manual element becomes invalid after upstream deletion | Surface dependency validation/conflict; do not silently discard it           |
| V-10 | Explicit user requests validation without transformation                | Validate current stored model without changing Base or synchronization state |

Transformation synchronization uses the explicit model-transformation validation workflow and may
run the applicable semantic EVL profiles. This is separate from chatbot/LLM assistant apply,
repair, proposal, and commit paths: assistant-generated model outputs are gated only by structural
Ecore/EMF conformance through `ModelService.validateStructural(...)`, never by EVL.

## 13. Transaction, concurrency, and failure scenarios

| ID   | Scenario                                                      | Expected behavior                                                                                |
| ---- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| F-01 | ETL execution fails                                           | No Working/Base changes                                                                          |
| F-02 | Comparison fails                                              | No Working/Base changes; return diagnostic                                                       |
| F-03 | Conflict exists                                               | Persist session; do not partially commit safe changes to canonical Working                       |
| F-04 | Validation fails                                              | No Working/Base advancement                                                                      |
| F-05 | Working persistence succeeds but Base persistence fails       | Roll back transaction so neither advances                                                        |
| F-06 | Base persistence succeeds but Working persistence fails       | Roll back transaction so neither advances                                                        |
| F-07 | Two transformations target the same relationship concurrently | Serialize with locking; reject stale revision/fingerprint where necessary                        |
| F-08 | Client submits stale source revision                          | Reject before transformation commit                                                              |
| F-09 | Client finalizes the same session twice                       | First succeeds; later request receives not-found/already-closed behavior without a second commit |
| F-10 | Backend restarts with a pending session                       | Reload durable session and continue if revisions/fingerprints still match                        |
| F-11 | Temporary files or resources fail to clean up                 | Report operational issue without changing semantic transaction outcome                           |
| F-12 | API job is retried with same idempotency key and fingerprint  | Return/reuse the same logical job result rather than performing a duplicate commit               |
| F-13 | Same idempotency key is reused for different input            | Reject key/fingerprint mismatch                                                                  |
| F-14 | User lacks project/model permission                           | Reject without disclosing or changing synchronization state                                      |

## 14. Multi-cycle evolutionary scenarios

| ID   | Evolution sequence                                                                     | Expected behavior                                                                                                   |
| ---- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| E-01 | Generate v1 → refine → upstream v2 → merge → upstream v3 → merge                       | Each accepted raw generation becomes the next Base; refinements remain distinguishable                              |
| E-02 | Manual edit survives several generator no-op cycles                                    | Preserve it indefinitely until user or a resolved conflict changes it                                               |
| E-03 | Generator changes an unrelated feature in every cycle                                  | Apply each change while retaining manual refinements                                                                |
| E-04 | User accepts generated value after earlier manual refinement                           | Accepted result becomes Working; raw NewGenerated becomes Base, so future unchanged runs are clean                  |
| E-05 | User keeps manual value through repeated generator changes                             | Each new incompatible generator change can create a new conflict because Base advances only after acceptance        |
| E-06 | Generated element is manually refined, deleted upstream, kept, then later reintroduced | Match by stable identity where appropriate and compare against the accepted baseline history                        |
| E-07 | User-created downstream element later gains a generated analogue                       | Do not merge merely by name; reconcile only through explicit identity/migration policy                              |
| E-08 | Source rename followed by edit and later deletion                                      | Preserve target identity through rename/edit; treat final disappearance as generated deletion                       |
| E-09 | Earlier PIM refinement changes subsequent PIM→PSM output                               | Treat accepted PIM Working as the PSM transformation source and synchronize against the PSM relationship's own Base |
| E-10 | Model evolves forward, then user restores an older upstream revision                   | Treat the restoration as a new current source state and perform normal three-way comparison, not database rollback  |

## 15. PSM-to-artifact regeneration scenarios

Artifacts are files, not EMF model elements. Their preservation rules differ from CIM→PIM and
PIM→PSM synchronization.

| ID    | Scenario                                                  | Expected behavior                                                                                 |
| ----- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| AR-01 | First artifact generation                                 | Create the complete generated artifact set                                                        |
| AR-02 | Same PSM regenerated unchanged                            | Produce equivalent artifacts without duplicates                                                   |
| AR-03 | PSM adds generated resource                               | Add corresponding files/sections                                                                  |
| AR-04 | PSM edits generated resource                              | Regenerate generator-owned file regions                                                           |
| AR-05 | PSM deletes generated resource                            | Remove obsolete generator-owned output according to artifact lifecycle rules                      |
| AR-06 | User edits a protected region                             | Preserve protected content during regeneration                                                    |
| AR-07 | User edits generator-owned text outside protected regions | Generator may replace it; UI/docs must make ownership clear                                       |
| AR-08 | Protected-region markers are malformed or duplicated      | Fail safely and report the file/region instead of silently losing manual code                     |
| AR-09 | Generated file conflicts with independent user file       | Use explicit ownership/path policy; do not silently overwrite unknown user content                |
| AR-10 | Artifact generation fails midway                          | Publish atomically or retain previous artifact set; do not expose a partial release as successful |

## 16. End-to-end scenario families

A complete progressive modeling test campaign should combine the atomic cases above into these user
journeys:

1. Import CIM, validate, generate PIM, validate, generate PSM, validate, and generate artifacts.
2. Add CIM elements and verify generated PIM/PSM additions and artifact changes.
3. Edit CIM features and verify safe propagation through both downstream levels.
4. Delete CIM elements and verify safe deletion of untouched generated subtrees.
5. Manually refine PIM, change unrelated CIM content, and verify both changes survive.
6. Manually refine PIM, incompatibly change the same CIM-derived state, and resolve both
   `KEEP_USER` and `TAKE_GENERATED` variants.
7. Manually refine PIM, delete its upstream CIM source, and resolve the delete/change conflict both
   ways.
8. Manually delete PIM content, then change its CIM source, and resolve restore-versus-delete.
9. Add independent PIM content, regenerate from CIM, and verify preservation.
10. Repeat scenarios 5–9 at PIM→PSM, including nested AWS resources and cross-references.
11. Mix multiple safe changes and multiple conflicts in one synchronization session.
12. Modify Working or upstream while a conflict session is pending and verify stale-session
    protection.
13. Repeat accepted generations to prove idempotence and stable identities.
14. Evolve CIM, PIM, and PSM through at least three accepted cycles and verify each raw baseline.
15. Regenerate artifacts while preserving valid protected regions and removing obsolete generated
    output.

## 17. Required invariants for every scenario

Regardless of the scenario, all correct implementations must preserve these invariants:

1. Transformation always generates into a fresh empty target model.
2. Base, Working, and NewGenerated are distinct model states and independent EMF graphs.
3. Stable immutable IDs—not names—are the primary matching mechanism.
4. User-created elements remain unless explicitly deleted or involved in a resolved conflict.
5. Real conflicts never silently destroy either side.
6. Safe changes may be prepared in a candidate, but canonical Working is not partially committed
   while conflicts remain.
7. Canonical Working and raw Base advance atomically only after successful validation.
8. Base advances to raw NewGenerated, never to merged Working.
9. Cancelled, invalid, failed, or stale sessions do not change canonical Working or Base.
10. No accepted model contains missing IDs, duplicate IDs, unresolved proxies, dangling references,
    wrong-type references, duplicate roots, or incomplete required containment.
11. Repeating an unchanged transformation is idempotent.
12. Traceability remains consistent with accepted source and target identities.
