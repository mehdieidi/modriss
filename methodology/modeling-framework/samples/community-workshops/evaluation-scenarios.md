# Evaluation scenarios

## Reference fixture

Use a fresh application dataset and evaluation project for each independent scenario, except the explicitly sequential narrative S01–S03. Keep test identity accounts stable and reset workshop, registration, notice, audit, and idempotency data. Do not reset through an application feature that is outside the scope of the participant task. Assign a fixed clock and a delivery test double when refining the generated application; these are experiment facilities, not additional participant features.

These are proposed experimental materials, not a validated study protocol. Pilot for clarity and duration before recruiting a formal sample. Never show the reference CIM to participants asked to construct a model from requirements until their construction task is complete.

| Request keys                              | Distinct per new command; preserve the original key and payload for replay tests                       |

UTC is the fixture display timezone. In a timezone presentation test, change the centre timezone and verify equivalent instants and an explicit timezone label. The future fixture dates avoid depending on the actual execution date. Relative-time tests must advance the controlled clock, not wait for real days.

For notice tests, inspect application intent/attempt records and the provider double's accepted-key ledger separately. For retention, inspect every scoped store rather than only checking that a booking disappeared from a screen.

## Suggested participant activities

Keep modeling evaluation separate from evaluation of the generated booking application. A participant can understand the domain without knowing cloud services; an expert who reviews PIM/PSM decisions needs an appropriately different task.

| Activity             | Materials and task                                                                                                                                                                                                                  | Evidence                                                                                                                               |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Domain comprehension | Provide README and requirements. Ask the participant to explain what happens to Cara when Alice cancels, what happens at the exact cutoff, and whether delayed email changes a booking.                                             | Answers, misunderstandings, time, and requests for clarification; use to pilot the materials.                                          |
| CIM construction     | Use an empty CIM project and the same requirements. Ask the modeler to represent the seat request, waiting rules, cancellation/promotion, and essential notice behavior. Disclose training and assistant availability consistently. | Task time, authored model, explicit validation results, coverage of selected requirement IDs, help requests, and error corrections.    |
| CIM inspection       | Import the reference XMI. Locate the capacity invariant, FIFO rule, authorization rule, retry timing, and retention scope; predict S02 and S04.                                                                                     | Navigation success, prediction accuracy, explanation quality, and time.                                                                |
| Refinement review    | Generate the draft PIM. Identify decisions needed to preserve atomic allocation and durable notice obligations; refine the deadlines and authorization boundaries. Continue to AWS PSM and artifact generation.                     | Trace links, resolved/manual decisions, model revisions, generated artifact references, and any lost or altered requirement semantics. |
| Runtime acceptance   | After business implementation, have an end-user perform S01/S02 using participant/organizer accounts; run technical/fault scenarios separately.                                                                                     | Observable booking statuses, waiting order, roster counts, notice ledger, workload measurements, and linked test results.              |
| Controlled change    | In a separate copy, change waiting-list maximum from ten to five in requirements and affected model elements; predict the change to S08, refine and regenerate. Keep the original baseline unchanged for comparison.                | Correctly identified impacts, retained manual refinements, regenerated differences, trace updates, and revised acceptance result.      |

Use a pilot to choose time limits and task subsets. Do not assume every participant should construct all 352 model elements; a bounded modeling slice and a complete reference inspection are different treatments. Keep training, starting artifacts, task wording, assistant access, dataset, provider faults, and clock settings comparable across conditions. If comparing conditions, counterbalance task order and report prior modeling/cloud familiarity. Record facilitator intervention and abandoned tasks as well as successes; preserve raw observations before applying a scoring rubric. No statistical validity or participant sample size is claimed here.

## End-to-end evidence chain

1. **CIM:** import, inspect, save/export/reimport, and explicitly validate. Check R01–R21 and requirement-to-domain links.
2. **PIM:** generate a draft, inspect trace/readiness outputs, complete contracts, transactions, authorization, delivery recovery, timers, and retention. Explicitly validate the reviewed PIM.
3. **PSM:** map the reviewed PIM to AWS, review resource identities, permissions, persistence, schedules, retry/dead-letter behavior, retention and observability. Explicitly validate the reviewed PSM.
4. **Artifacts:** generate, inspect protected regions/manual actions, complete business logic, and build the resulting application. Keep generated code distinct from completed code in the recorded evidence.
5. **Runtime:** deploy to the chosen test environment, run scenario oracles, and retain requirement/test/trace identifiers with results. A successful generator execution alone is not a passed application acceptance test.

Record the repository revision, sample XMI hash, configuration, model revisions, tool versions, generated versus manually completed work, validation reports, scenario results, environment and fault settings, and evidence locations. This lets experts assess both modeling support and the amount of work needed to reach a functioning application.
