The product idea

Low-code without losing the engineering evidence.

Modless is being built as an academic thesis and a production-oriented platform. Its central claim is careful: automation should accelerate serverless development, but it should not hide the architectural rationale, compliance obligations, security choices, transformation assumptions, or manual decisions that make a system safe to operate.

The repository implements that claim as a staged model-driven engineering pipeline: formal DSMLs for CIM, PIM, and AWS PSM; EVL validation rules for semantic quality; ETL model-to-model transformations that produce reviewable drafts; and EGX/EGL model-to-text generation that emits a deployable AWS project with trace reports, protected regions, tests, scripts, and operational documentation.

01

Begin with a computation-independent business model.

The first state is intentionally not cloud-shaped. It contains business goals, KPIs, stakeholders, actors, roles, capabilities, bounded contexts, ubiquitous language, domain entities, value objects, aggregate candidates, commands, queries, events, processes, policies, decision tables, risks, assumptions, hotspots, and readiness evidence.

02

Refine the CIM by hand before automation makes architecture decisions.

Analysts and domain owners can add the details that a transformation should not invent: appeal policy, human review ownership, identity evidence risk, KPIs, assumptions, hotspots, readiness findings, and manual decisions. The visual shows those changes being attached to real CIM concepts instead of floating as generic notes.

03

Transform CIM intent into a provider-independent serverless draft.

The CIM-to-PIM ETL pipeline is split by concern: root scaffolding, boundaries and security, domain data, behavior and contracts, process and policy, and integration and deployment. It creates trace links, readiness checks, generated markers, and manual decisions so uncertain mappings are visible instead of silently baked into architecture.

04

Use the AI modeling assistant to edit the PIM in real time.

The demo prompt asks for an appeal review path when identity evidence is missing. The assistant applies metamodel-safe edits by adding a HumanTask, WorkflowState, AccessPolicy, and ReadinessCheck to the PIM. The animation shows the prompt, the assistant response, and the live edits appearing on the model canvas.

05

Review the PIM manually before selecting AWS resources.

Architects can refine authorization, data access patterns, workflow semantics, retries, idempotency, retention, cost hints, observability, and validation results while the model is still provider-independent. That is where service shape and contracts should be reviewed before they harden into AWS resources.

06

Move from provider-independent architecture to concrete AWS design.

The PIM-to-AWS-PSM transformation realizes functions as Lambda resources, APIs as API Gateway structures, data stores as DynamoDB, object stores as S3 buckets, queues as SQS, topics as SNS, event channels as EventBridge, workflows as Step Functions and ASL, identities as Cognito, and policies as IAM, KMS, Secrets Manager, SSM, and CloudWatch concerns.

07

Review AWS-specific risk before artifact generation.

The AWS PSM is not treated as a black-box output. It has stages, SAM stacks, naming and tagging policy, security baseline, relationship views, documents, trace model, and production-readiness assessment. Blocking questions such as region choice, authorizer design, DynamoDB keys, DLQs, alarm thresholds, IAM wildcard review, secret rotation, and production approval stay attached to the model.

08

Generate artifacts, then refine the code regions humans should own.

The EGX/EGL generator emits SAM templates, Go Lambda handlers, OpenAPI, ASL, schemas, fixtures, tests, CI workflows, runbooks, trace JSON, security reports, and manual-action reports. Generated handlers include protected regions for custom validation, business logic, error mapping, tests, and deployment notes, so final code refinement remains deliberate instead of being overwritten.

Formal DSML stack

Three modeling languages, one shared traceability kernel.

The shared kernel gives every level a common language for identity, lifecycle, annotations, expressions, trace links, structured documents, production readiness, readiness findings, readiness checks, and manual decisions. Each DSML then adds the concepts appropriate to its abstraction level.

Transformation methodology

Automation that explains itself.

The transformations do not simply draw target nodes. They preserve source model identity, create trace links with confidence, mark generated elements, add readiness checks, and surface manual decisions when the correct architectural choice depends on human knowledge.

From AWS PSM to project artifacts

The generator emits a deployable skeleton and the evidence around it.

Modless generates more than infrastructure. It emits source code entry points, contracts, fixtures, tests, documentation, runbooks, scripts, CI workflows, and trace reports. Machine-owned files are overwritten when they must remain valid, while developer-owned areas use protected regions.

AI-assisted modeling

A modeling assistant belongs inside every level of the pipeline.

The frontend already expresses the assistant interaction model: sessions are scoped by CIM, PIM, or PSM; messages include the current serialized model; realtime channels can return assistant responses and model updates; and the canvas can refresh when an assistant-generated model is accepted. In the product vision, that assistant is aware of the active metamodel and validation constraints, so prompts become model-safe edits.

Research-grade sample

Climate relief grants is the kind of workload Modless is built to model.

The sample case study models a regional public agency handling emergency microgrants and supplier reimbursements after floods, heatwaves, wildfires, and infrastructure failures. It is intentionally bursty, integration-heavy, event-driven, compliance-heavy, and filled with human review moments.

That makes it ideal for evaluating the entire approach: business goals and KPIs, bounded contexts, regulated personal and financial data, eligibility commands and audit queries, event-driven processes, manual appeal workflows, privacy constraints, readiness risks, transformation assumptions, and generated AWS serverless artifacts.
